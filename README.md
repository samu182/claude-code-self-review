# self-review

AI（Claude Code）と一緒に書いたコードを、PR を出す前に自分でレビューするための手順です。
Claude Code のスキル（`SKILL.md`）として書いています。

目的は1つだけです。**レビュアーに、同じ型の欠陥を二度見つけてもらわないこと。**

---

## 何に困っていたか

AI と一緒に開発するようになってから、書く速さは上がりました。一方で、レビューで受ける指摘の型が繰り返されていました。

- 「この1行を消しても、テストが全部通る」
- 「本文に書いてあることが、現物と違う」
- 「失敗しても、誰にも分からない形になっている」
- 「別の利用者の画面で開くと、見えてはいけないものが見える」

AI に「厳しくレビューして」と頼むこともしていましたが、同じ型の指摘は減りませんでした。

調べると、理由ははっきりしていました。

- **決まった形を持たない自己レビューは、自分の欠陥の2割も見つけられない**（チェックリストを持つと7割を超える。PSP の研究）
- **LLM は外からの手がかりが無いと、自分の誤りの「場所」を見つけられない。** 同じ会話の中で「見直して」と頼むと、かえって精度が下がることもある

つまり、「頼み方」の問題ではなく「手順の形」の問題でした。

## 何を作ったか

過去の指摘と事故の記録を1件ずつ見直し、欠陥の型を **6つの視点** に分けました。

| 視点 | 見ること |
|---|---|
| 0 説明できるか | 差分を自分の言葉で説明できるか。本番の今の状態・外部の仕様を、記憶でなく現物で確かめたか |
| 1 権限 | 本人・別の利用者・管理者のプレビュー・未ログインの4つの目で、見えるもの・変えられるもの |
| 2 無音 | 壊れたことが誰にも分からない形で壊れていないか |
| 3 同時・時間・順序 | 受け取ったときと使うときの時差・逆の順で届く知らせ・別の道から同じ状態・二重クリック・期限 |
| 4 二重実装 | 同じことをする実装がもう1セット無いか |
| 5 消えたガード | 差分の「消えた側」だけを読む。AI が防御のコードを消していないか |
| 6 書いたことは本当か | 本文・計画・手順書の数字と主張を現物と突き合わせる |

形の上で工夫したのは、次の3つです。

1. **視点ごとに別の AI（subagent）に見せる。** 1つの AI に全部を渡さない。視点が互いに補い合う効果が消えるからです。実際、独立に回した別々の視点が、同じ重大バグに行き着いたことがあります。
2. **最後に、わざとコードを壊してテストが落ちるかを確かめる（ミューテーション）。** テストが全部通っていることを安心の材料にしません。壊す前に「どのテストが落ちるはず」と宣言してから走らせます。
3. **見つけたものは捨てない。** 直さないものも、却下したものも、理由を付けて台帳に1行残します。判断を誤っていたときに遡れるようにするためです。

## どう測っているか

手順を守ったこと自体を成果にしないために、見る数字を1つに決めています。

> **merge 後に見つかった実害のある欠陥の数**

導入前の期間を基準線にして、下がらなければ手順を捨てるか作り直します。
あわせて、回すたびに「どの視点で何件当たったか」を1行ずつ記録しています。空振りが続く視点でも、記録が貯まるまでは減らしません。年に数回しか当たらない視点（権限）ほど、当たったときの被害が大きいからです。

## 棚卸しで分かったこと・直したこと

この手順は、merge 済みの PR を見直す「棚卸し」の結果で直し続けています。これまで 2 回やりました。

| | 何を数えたか | 分かったこと | 直したこと |
|---|---|---|---|
| 1 回目 | レビュアーの指摘を「どの視点で拾えたはずか」で仕分けた | 差し戻しと実害のある指摘は減っていた。それでもいちばん多い型は「この1行を消してもテストが全部通る」。自分が壊した所は毎回落ちていたのに、同じ PR で穴が見つかっていた。自分は「PR の目的の1行」を壊し、レビュアーは「つなぎの1行」（呼ぶ側が値を渡す1行・部品をつなぐ1行・偽物の下の本物の処理）を壊していた。「小さいから」と外した視点から指摘が出ていた。本文と現物のずれを見る視点が無かった | つなぎの1行を毎回撃つ。視点を外すのは見る対象が差分に無いときだけ。視点6（書いたことは本当か）を足し、手順書や計画の docs でも回す。権限を「4つの目 × 見る／変える」の表で、許可と拒否を2本1組でテストする |
| 2 回目 | 複数のリポジトリで、merge 後に見つかった欠陥を元の PR まで遡り、すり抜けた理由で分けた | 漏れの多くは**手順が回っていなかった**所から出ていた（回すはずの PR で回していない・外してはいけない視点を外した・会話を引き継ぐ subagent で回していた）。後回しにした「無音」が、本番につないだ日にそのまま起きた。回したのに漏れたものは、**時間と順序**（受け取ったときと使うときの時差・外部の知らせが逆の順で届く・別の道から同じ状態に着く）と、**読んでも見つからず動かせば出る型**（判定を変えて外れた入力・偽物が本物の失敗の仕方を持たない）に集まっていた | 視点は、差分と視点だけを渡した新しい subagent で回す。PR を出す前の確かめで、記録が無ければ止める（`ship-pr` の側で止めている）。本番につなぐ PR では、差分が触る経路の台帳の未解決を全部引いて判定し直し、無音を後回しにするなら検知だけはその PR で入れる。視点3 を「同時・時間・順序」に広げた。「壊す」を「動かして確かめる」に広げた（壊す候補を全部書き出す・判定を変えたら前後で同じ入力を流して比べる・偽物に本物の失敗の仕方を持たせる・SQL は本物の DB に一度通す） |

すり抜けを直すときは、先に「回していなかった／後回しにした／型が外だった」に分け、視点を足すのは3つ目のときだけにしています。

直した後の期間はまだ短く、本物の利用者もまだ少ないので、効いたかどうかはまだ言えません。

## 使い方

1. `SKILL.md` と `views/`（視点1〜6の本文。視点ごとの subagent だけが読む）を、Claude Code のスキルのフォルダ（`~/.claude/skills/self-review/`）に置きます
2. PR を出す前に「レビューして」と頼むか、`/self-review` で呼びます
3. 記録は `~/.claude/local/self-review-tally.md` に1行ずつ足していきます（手元だけに置き、チームのリポジトリには書きません）
4. 計画書・台帳の場所など、自分の環境の決まりは `~/.claude/local/self-review.md` に書いておくと、先に読まれます

手順の中には、特定の技術（Next.js、Supabase の RLS など）を例に出している所があります。ほかの構成で使う場合は、例を読み替えてください。
