# 視点1 — 権限の違う目 / 同一性（実害が最大。ここが最大の盲点）

**利用者に届く実害はここから出やすく、しかも通常のコードレビューではほとんど見つからない。** 作る側の目で何度見ても正しく見えるのが特徴。

- **同じ画面を、4つの目で開いたら何が見えるか**を1つずつ書く
  - 利用者のセッション（例: RLS で自分の行と、紐付いた行だけ）
  - 管理者（権限の段階があるなら段階ごと）
  - 管理者のプレビュー（管理者が利用者の画面を代わりに見る機能）
  - 未ログイン / 別の利用者
- **画面の判定とデータ取得が、同じ利用者を見ているか。**
  実例: 表示はプレビュー先の利用者で判定しているのに、データ取得にプレビュー先を渡しておらず、サーバーは管理者自身のセッションでデータを引いていた
- **新しい口（画面・API・一覧・検索・書き出し・ファイル・定期実行の結果）を足したら、認可の判定（ガード・middleware）が掛かっているかを口ごとに数える。** 同じデータに届く別の口も数える。判定が確かめられないとき（ヘッダーが空・設定が空・相手が答えない）に通す側へ倒れていないか。既定は拒否
  （書籍 p158・p160・p162・p415。実例: 社内向けの確認画面を鍵なしで本番のデータにつないだ。middleware の「拒否」の枝が素通しになっていた。空のヘッダーを「信用する」側に倒していた）
- **id で引いて、持ち主で絞っているか。** 特権キー（RLS を通らない経路）で持ち主の確認が抜けていないか。RLS の `USING (true)` が意図した公開か漏れか
- **相手が選べる値（URL・クエリ・hidden・JSON・ヘッダー・メールアドレスのような名乗り）で、対象や本人を決めていないか。** 決めるなら、ログインした本人との関係と今の状態を、取得・更新の条件に入れる
  （書籍 p153・p155・p159・p387。実例: 押した側が送った id だけで引いて、他人の注文を取り消せる形だった。名乗ったメールアドレスだけで本人とみなし、他人の情報を返す形だった）
- **同一性・多重度**
  - この利用者の行は1つか。表記ゆれでレコードが割れていないか
  - `N対1` を `1対1` と誤認していないか（実例: 外部システムの N件 × 自システムの1件を、N個の正常な1対1と誤認して別案件へ自動転記した）
- **権限を表にして、許可と拒否を2本1組で確かめる。** 行 = 4つの目（本人 / 別の利用者 / 管理者のプレビュー / 未ログイン）、列 = 見る / 変える。マスを全部埋め、拒否のマスはテストで「拒否された」と「データが変わっていない」の両方を見る。許可のマスは「普通に使える」テストを対で置く（全部拒否する直し方でも拒否のテストは通るので、許可側が無いと守れていない）
  （書籍『BUILD · BREAK · FIX · VERIFY』p152・p163・p535。実例: 片方の向きのずれだけを見落としてもテストが緑だった——対で書けば拾えた）
- **既存の口を通って、新しく足した値が誰の目に届くか。** 利用者に返る JSON・メールの件名と本文・画面・ログ。社内向けの語や担当者の実名が利用者側に出ないか
  （実例: 担当者の実名が利用者のブラウザまで届いた。社内向けの件名が利用者宛てメールの件名になりうる形だった。管理者のプレビューで押せないボタンが出ていた）
- **返す JSON は、返してよいキーの集合をテストで固定する**（`set(keys) == {...}` の形）。DB の行や外部 API の応答を、そのまま返さない・画面に写さない・AI への指示に入れない
  （書籍 p388・p397・p398。実例: 記録の失敗の列が絞られず、外部の応答の本文まで出る形だった。差し込んだ値の制御文字が AI への指示にそのまま届いた）
- **秘密**: 鍵の直書き、ブラウザに配られる環境変数（例: `NEXT_PUBLIC_`）での露出、AI の道具の出力への秘密値の混入
- **URL・ログにトークンや個人情報を載せていないか**（メールのリンク・署名・クエリ文字列を含む）。**メール内のリンクを、届いたリクエストの Host / X-Forwarded-Host から組み立てていないか**（設定値から作る。書籍 p113・p481）
