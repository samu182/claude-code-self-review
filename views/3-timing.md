# 視点3 — 同時・時間・順序（1人で順番に、すぐに触ると絶対に出ない）

**同じ瞬間に2つ・時間が経ってから・思っていない順で、の3つを見る。** 棚卸しで、merge 後のすり抜けがいちばん集まっていたのは後の2つだった。

時間・順序:

- **受け取った時点と使う時点の時差。** 受け取ったときに正しかった値（日時・期限・候補・状態）が、使うときにも正しいか。過ぎた日時のまま進まないか
  （実例: クーポンを画面に出したあと時間が経ってから使われ、期限の切れたクーポンのまま注文が通った）
- **外部の知らせが遅れて・逆の順で・二度届いたら。** webhook・イベント・コールバック・非同期の結果は、送った順にすぐ届くとは限らない。終わったあとに「始まった」が届く・失敗の知らせが成功のあとに届く、を1つずつ追う
  （実例: 外部の結果の知らせが遅れて届き、先に進んだ状態を古い状態で上書きした）
- **同じ状態に、別の道から着いたら。** 新しく状態に着く道（画面・操作・取り込み）を足したら、その状態を読み書きしている**差分の外の**見張り・集計・定期実行・取り込み・通知を `git grep` で全部数え、新しい道から着いた行でも同じ判定を通るかを見る
  （実例: 管理画面から発送済みにできる道を足したが、見張りの SQL は元の道の印だけを見ていて、発送済みの注文で警告が鳴り続けた）
- **翌日・週明け・月末・日をまたぐ処理**で、定期実行の時刻と業務の時刻がずれたときに、1回飛ぶ・二度走ることがないか

同時:

- **二重クリック**（実例: 2本とも状態の判定を通り、1本目が紐付けに成功、2本目が失敗して空の値で上書きし、紐付けが永久に消えた）
- **並行タブ・別経路からの同時更新**（実例: 読み込み → 外部の計算で数秒 → 全列上書き、の間に別の更新が入ると消える）
- **切断・タブ閉じ**（実例: 切断後の書き込みが例外を投げ、catch が全部を外部の障害として扱って、できていた結果を捨てた）
- **長い処理の待ち方**（実例: 1つのリクエストの中で重い書き出しの完了を待ち、上限の時間で落ちた。同じ仕組みの非同期版が別の所にあったのに使っていなかった）
- **外部を呼ぶ処理すべてに期限（タイムアウト）があるか。** 外部 API・メール送信・DB の鍵の返却・集計の通信。期限が無いと、記録が消える・ボタンが理由なく押せないまま残る
- **状態を変える操作は、「今の状態 × 操作 × 誰が」の表を書き、禁止のマス（済んだものをもう一度・取り消したあと・古い画面から）をテストにする。** 更新の条件に今の状態を入れ、更新件数が 0 なら先へ進まない。拒否したときに通知・メールが出ていないか
  （書籍 p406・p409・p412・p418。実例: 決済の結果があとから届き、同じ人に注文確認のメールが 2 通届く形だった）
- **retry で二重実行にならないか**（知らない状態が retry 側に落ちる経路が無いか）
- **画面の状態の寿命。** 閉じて開き直したとき・開いている間に中身が変わったとき・最初の値で固定された state が古くならないか。表示を切り替えるだけで両方描いたままか、消えるか
  （実例: 開き直しても履歴一覧が古いまま。開いている間に対象が変わり、入力欄が2か所に出た。送信後に古いボタンを押すと何もできない画面になった）
